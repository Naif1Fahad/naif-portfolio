Case studies

Three problems nobody assigned him

Situation, action, result — with the numbers. Each one started outside the job description and ended as owned, delivered work. Details are generalized to respect confidentiality; every outcome is backed by dated records.

01
CASE 01 · PRE-RELEASE DEFECT HUNT

The launch that almost shipped broken payments

Situation

A patient-facing mobile app was weeks from public release. Booking and payment — the app's core value path — had passed developer testing. As the newest QA on the team, he owned the pre-release sweep.

Action

Designed scenarios beyond the happy path: zero-priced care packages, freshly created accounts with incomplete profiles, deliberately failed payments. Filed each break as a Highest-priority defect with reproduction steps, screenshots, and screen recordings — then retested every fix the day it landed.

Result

A chain of six Highest-priority payment defects — including bookings that silently vanished after a failed payment — was found, fixed, and verified before a single real patient hit the flow.

100% of the payment-defect chain verified closed pre-release. The failure mode that would have generated invisible lost bookings — and support calls with no trail — never reached production.
02
CASE 02 · SELF-INITIATED SECURITY PROGRAMME

From bug hunter to security-hardening programme

Situation

Platform APIs handling patient data were approaching a ministry-facing deployment. Functional testing was covered; dedicated security testing wasn't anyone's job.

Action

Built SQL-injection, auth-bypass, and input-validation test collections from scratch, wrote a Python rate-limit test, and mapped API routes no client actually consumed. Packaged the findings the way leadership needed them: an executive deck, a management dashboard, a tracker, and a hardening checklist.

Result

Security hardening became a tracked programme with management visibility rather than an ad-hoc concern. Findings were remediated before the deployment, and an RBAC role-by-permission matrix formalized access governance.

An entry-level hire created the security-testing function. The P0 security pack and checklist are now reusable assets the team runs against every ministry-facing release.
03
CASE 03 · END-TO-END CYCLE OWNERSHIP

Running a national screening platform's test cycles

Situation

A national breast-cancer screening platform was in intensive fix cycles, with defects arriving faster than they were being verified and no repeatable process for the cycle itself.

Action

Took ownership of the full defect lifecycle — structured trackers, valid-and-invalid test-data sets, verification cycles 28 through 38 — while coordinating fixes across developers, clinical stakeholders, and ministry-side reviewers. Then wrote the test-cycle guide and evidence-capture guide so any tester could replicate the process.

Result

Fix verification became documented, dated, and repeatable. The defect reports fed a module rebuild, and the guides now onboard other testers onto the programme.

Eleven verification cycles run and documented end to end — the process survives without him, which is the point.

Artifact 02

Test design: beyond the happy path

Excerpt from a vitals-data upload suite — the valid, boundary, and invalid sets that catch what happy-path testing misses.

InputCase typeExpected behavior
Blood pressure 120/80ValidAccepted, stored, shown on timeline
Heart rate 0BoundaryRejected with a clinical-range message
Temperature 45.1 °CBoundaryRejected — above survivable range
Date of reading in the futureInvalidRejected with a clear field-level error
Empty file / wrong template columnsInvalidBulk upload refused with row-level report

Every suite ships in two files — a VALID set that must pass and an INVALID set that must fail — so a regression in either direction is caught.

Artifact 03

The automation pattern

From the Playwright + pytest framework: page objects keep selectors in one place, test IDs map back to the manual Excel suites, and traces capture every failure.

# pages/booking_page.py — one page object, one source of truth for selectors
class BookingPage:
    def __init__(self, page):
        self.page = page
        self.book_now = page.get_by_role("button", name="Book Now")
        self.error_banner = page.locator("[data-test=error-banner]")

    def book_slot(self, physician, slot):
        self.page.get_by_text(physician).click()
        self.page.get_by_text(slot).click()
        self.book_now.click()

# tests/test_booking.py — TC-BOOK-014 maps to row 14 of the manual suite
def test_zero_priced_package_completes_booking(booking_page):
    booking_page.book_slot("Dr. Example", "09:00")
    expect(booking_page.error_banner).to_be_hidden()   # the bug this guards against shipped once — never again
